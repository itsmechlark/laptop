# Inside one turn of the cycle

The five phases are in `SKILL.md`. This is the judgment inside them: how big a
step to take, what separates a test worth keeping from one that only looks like
a test, what refactoring is allowed to mean, and what to do when the loop stalls.

## How big a step?

Three ways to reach green. Picking the wrong size is what makes a loop stall —
too large and the test stops constraining the code, too small and you spend the
session on arithmetic.

**Obvious implementation.** You can see the real code and it's small: write it.
This is the default and most cycles never leave it.

**Fake it.** Return the constant the test expects. Then write a second test the
constant cannot satisfy, and let that force the generalization.

```
# test 1: fee_for(2) == 0
def fee_for(guests) = 0          # obviously wrong, and green

# test 2: fee_for(9) == 50       # the constant can't survive this
def fee_for(guests) = guests > 8 ? 50 : 0
```

Reach for this **the moment you notice you're guessing**. It converts one hard
problem into two easy ones, and it guarantees the second test is meaningful:
you have proof the code fails it before you write the code that passes it.

**Triangulate.** When you can't see the general rule even after faking it, add a
second and third concrete example and let the shape fall out of them. This is the
expensive option — reach for it when the rule is genuinely unclear, not as a
default, or you'll write three tests where one would have done.

**The tell you picked wrong:** you are writing production code and cannot say
which line of the test demanded it. Stop; the step is too big.

## Reds worth keeping

A test that cannot fail is worse than no test — it costs a run every CI build
and reports success forever.

- **Tautological.** The assertion recomputes the answer the way the code does:
  `expect(total(a, b)).to eq(a + b)`, a snapshot generated by the code it
  checks, a constant asserted equal to itself. It passes by construction.
  Expected values come from somewhere independent — a worked example, a literal
  you calculated by hand, the spec.
- **Asserting the mock.** The body's Gotchas cover this one; it belongs here
  because it is the most common way a test ends up unable to fail.
- **Two behaviors in one test.** When it fails you learn that one of two things
  broke. Split it; the name will tell you which one to write.
- **Named for the implementation.** `test_calls_update_column` pins the method
  you happened to use. `test_marks_the_booking_confirmed` pins the behavior, and
  survives the refactor.

## Greens worth keeping

- **Minimal means minimal.** `search(term)` — not `search(term, fuzzy:, limit:,
  scope:)`. Every parameter no test asked for is a guess about the future you'll
  be maintaining either way.
- **Wrong-but-green is a legitimate waypoint**, not a failure. `return 0` on the
  way to a real calculation is the fake-it step doing its job. It stops being
  legitimate the moment you commit it as finished.
- **Don't refactor on the way to green.** Get the test passing, then clean up.
  Doing both at once means a failure has two possible causes.

## What refactoring is allowed to mean

Refactoring changes structure and preserves behavior. The tests are what make
that claim checkable, which is why it only happens after green:

- **In scope:** renaming, extracting a method or class, removing duplication,
  simplifying a conditional, moving code to where it belongs.
- **Out of scope:** anything that changes what the code does. That needs its own
  failing test first — it's the next cycle, not this one's cleanup.
- **Refactor the tests too**, and usually before the code — duplication in setup
  is the most common thing worth extracting. Don't weaken an assertion while
  you're in there; that isn't refactoring.

**If a refactor turns a test red, revert the refactor — never the test.** A
change that alters behavior was not a refactor. Re-do it in smaller moves,
staying green between each.

## When the loop stalls

**Two failed attempts at green means the step was too big.** Go back to the last
green and take a smaller one — usually by faking it. Pushing through a third
attempt is where the sessions go that end with untested code and a story about
why this case was different.

That needs a green you can actually return to, so keep the last one
identifiable. A checkpoint commit is the cheapest way, but it is still a commit:
ask for it once, up front, rather than assuming it — never commit unless
explicitly told (AGENTS.md's non-negotiables, and `git-commit`'s own first rule).
Without that go-ahead, note what the last green state was and revert by hand.

**Other stalls and what they mean:**

| The loop is stuck because… | What it's telling you |
| --- | --- |
| You can't write the assertion | The behavior isn't specified yet. Go get the answer; don't invent one and pin it. |
| The test needs half the system built first | You started too low. Move up a layer and let the higher test tell you what's actually needed. |
| Every green breaks a different test | The behavior you're adding conflicts with behavior already specified. One of the two is wrong — decide which before writing more code. |
| The same test has gone red and green four times | You're tuning the implementation against the test. Stop and read the failure properly, or revert to green and re-approach. |
